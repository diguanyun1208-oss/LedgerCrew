# LedgerCrew「账清社」三人任务清单

**Junction China 2026｜40 小时｜Microsoft Agent Framework Python 版**

参赛题目：**账清社——一个人经营的 MiMo 多智能体对账服务公司。**

目标：面向小型工作室，跑通「下单 → 上传票据与流水 → AI 协作 → 发现异常 → 老板决定 → 报告交付」的一笔完整服务订单。

本文件是三位开发成员的执行清单。完成任务后，在对应复选框打勾，并在 PR 中引用任务编号。H0 表示团队开始执行本计划，后续时间均为经过小时数。

## 接口与数据约定

### 角色与框架责任

| 角色 | 输入 | 输出 |
| --- | --- | --- |
| 运营总管 | 订单、材料和任务成果 | 下一项合法任务、交接或人工待办 |
| 票据 Agent | 图片、文件标识 | 票据字段、来源及需人工确认项 |
| 核对 Agent | 票据与流水 | 调用确定性工具后的匹配和异常结果 |
| 客服 Agent | 异常及证据 | 核实问题和询问草稿 |
| 交付 Agent | 核对结果、异常和人工决定 | 报告摘要、说明与证据引用 |

**C 定义工作流；B 负责调用、存储、权限和恢复；A 只依赖业务 API。** 前端不直接提交模型历史、工具结果或框架内部审批消息。

### B/C 内部契约

```text
build_workflow(deps, checkpoint_storage, workflow_name) -> Workflow

deps：读取订单/文件/流水，调用对账服务，保存校验后的成果，读取人工决定与补充材料。

共享模型：
InvoiceRecord          票据字段、来源、需确认项
ReconciliationResult   匹配项、异常、差额、汇总及证据
ReviewRequest          待办、问题、证据、允许动作与版本
ReportDraft            摘要、明细、未解决事项、证据和版本
```

B 在 H2 前确定完整字段和样例，C 的 Agent 与工具复用这些类型。

### HTTP 接口

统一前缀 `/api/v1`。B 提供 OpenAPI，A 据此生成 TypeScript 类型。

| 接口 | 用途 |
| --- | --- |
| `POST /orders` | 创建订单和客户会话，服务端确定价格与模拟交易状态 |
| `GET /orders`、`GET /orders/{id}` | 获取当前身份可访问的订单及快照 |
| `POST /orders/{id}/files` | 上传票据或流水 |
| `POST /orders/{id}/runs` | 启动后台任务，立即返回运行标识 |
| `GET /orders/{id}/events` | SSE 获取进度、交接、异常与待办 |
| `POST /orders/{id}/messages` | 客户补充说明及材料 |
| `POST /approvals/{id}/decisions` | 请求补充、保留异常继续、批准或退回交付 |
| `GET /orders/{id}/report` | 老板查看草稿，客户查看已发布报告 |
| `GET /orders/{id}/report.csv` | 下载有权限访问的核对明细 |
| `POST /admin/session` | 老板口令登录 |
| `GET /health` | 健康检查 |

### 对账与状态规则

- 金额统一存储和传输为整数分；CSV 用 Decimal 解析。
- CSV 列固定为 `transaction_id,date,counterparty,amount,direction,remark`，方向为 `in` 或 `out`。
- 自动匹配要求：规范化交易方相同、方向一致、金额相等、日期相差不超过 3 天，且候选唯一。
- 同一票据或流水只参与一次确定匹配；重复、多候选、金额差异和缺失均保留为异常。
- 原始材料、模型提取、客户说明和人工决定分别保存；每项结果有来源引用。
- 报告由代码计算金额，AI 组织文字。未知字段和未核实说明必须明确标记。
- 审批绑定待办和报告版本，旧审批不能批准新报告；检查点恢复和重复操作不得重复写入或交付。

```text
draft → queued → running
running → awaiting_review / ready_for_delivery / failed
awaiting_review → waiting_customer / queued
waiting_customer → queued
ready_for_delivery → delivered
ready_for_delivery → queued（退回修改）
failed → queued（人工重试）
```

1. B 提交最小骨架后，分别建立 `feat/web-*`、`feat/api-*`、`feat/agents-*` 分支。
2. 每个可验证任务独立 PR，写明任务编号、实现内容、验证方式和已知问题。
3. A 负责最终集成；API 与共享模型变更由 B 确认，AI 结果类型变更由 B、C 共同确认。
4. 每 4 小时同步 10 分钟：已完成、阻塞、下一交付；尽早合并可运行的小改动。
5. 密钥、客户材料、数据库、检查点和运行日志加入忽略规则。
6. 只将完成且验证过的任务标为完成。真实调用、用户反馈与录像均按实际状态说明。
